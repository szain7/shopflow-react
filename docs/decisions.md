# Shopflow decisions

## Day 1

| Decision                                                                           | Reason and alternative                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Keep npm, the existing lockfile, and the installed React, Vite and ESLint versions | Keep the known foundation and add only Day 1 dependencies. Changing package managers or upgrading the app stack would increase the scope.                                                                                                                                                                                                                                                           |
| Use Tailwind 4.3.5 and its Vite plugin                                             | Semantic tokens live in CSS and the app uses utility classes on native elements. A separate PostCSS pipeline would duplicate Vite integration. See the [Tailwind Vite setup](https://tailwindcss.com/docs/installation/using-vite).                                                                                                                                                                 |
| Use TypeScript 5.9 and type-aware ESLint alongside Prettier                        | TypeScript checks app contracts, ESLint catches unsafe use and hooks mistakes, and Prettier handles layout. Syntax-only lint rules cannot catch unsafe use of values from JSON. See [typescript-eslint dependency compatibility](https://typescript-eslint.io/users/dependency-versions/).                                                                                                          |
| Keep both whole-repo and app lint commands                                         | The whole-repo command keeps reporting the existing exercise findings. The app command verifies Day 1 in isolation while preserving the exercises as written.                                                                                                                                                                                                                                       |
| Use native fetch with Zod                                                          | One client owns transport and maps responses to validated types and safe errors. A separate HTTP library is unnecessary for the six operations.                                                                                                                                                                                                                                                     |
| Use MSW in the browser and in tests                                                | Shared handlers exercise HTTP statuses, headers, cancellation and malformed responses. Stubbed client calls would bypass those boundaries. Vitest runs the integration suite and Testing Library checks the shell through accessible roles and keyboard interaction. See [MSW browser integration](https://mswjs.io/guides/integrations/browser) and the [Vitest guide](https://vitest.dev/guide/). |
| Keep mock auth in memory and store only order records in tab session storage       | Reload requires a fresh fake login while the mock can still recognize a repeated order key. An entirely in-memory ledger would forget prior submissions on reload.                                                                                                                                                                                                                                  |
| Use the plan’s local mock assumptions                                              | Contract gaps are documented in the [API contract](api-contract.md), including paging, filters, fake login, order state, idempotency, and test scenarios. A shared authoritative contract would take precedence.                                                                                                                                                                                    |

## Day 2

| Decision                                                              | Reason and alternative                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Use React Router 7.18.6 for routes and applied filters                | The URL restores shareable views and browser history. Keeping applied filters in component state would require a separate synchronization layer. Only the search draft is local. See the [React Router 7 search params API](https://reactrouter.com/7.18.6/api/hooks/useSearchParams).                                                                                                                       |
| Use TanStack Query 5.108.2 for paged product responses                | The key describes the filters, page or product ID, and active mock scenario. A 30-second stale time makes brief revisits responsive. Inventory may be stale during that window. Future order and live updates can invalidate product queries. Manual retry keeps failures reproducible. See [TanStack Query cancellation](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation). |
| Debounce search for 300 ms and suspend the results area while editing | Applying each keystroke would crowd history and start extra requests. Showing previous results while the draft differs would mislabel them. Unmounting the old results observer aborts its pending request. The new key isolates any late response.                                                                                                                                                          |
| Keep pages bounded to the contract's 24 items                         | Filtering and sorting belong on the server so the total represents the whole result set. Client filtering would only describe the current page.                                                                                                                                                                                                                                                              |
| Expose scenario URLs only when development mocks run                  | The shared typed client attaches a mock header in this mode. Production uses the normal API and SPA routing. The README documents the opt-in flag and host requirements.                                                                                                                                                                                                                                     |

## Day 3

| Decision                                                     | Reason and alternative                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use Redux Toolkit 2.15.0 and React Redux 9.3.1               | Cart and session are shared across routes. The checkout lock also needs to outlive a screen. Header count and total are selectors. Only cart IDs, quantities, and the name and cents needed for display are stored in the cart. Query owns product, account, and order responses. See [Redux Toolkit store setup](https://redux.js.org/toolkit/api/configureStore).                                                                                                                                                                                                                                                  |
| Validate separate storage records for cart and pending order | Local storage keeps the cart across reloads. Tab session storage keeps the frozen order body and key through a tab reload alongside the mock ledger. Memory-only intent would lose the identity needed for safe replay. Auth stays in memory.                                                                                                                                                                                                                                                                                                                                                                        |
| Replay ambiguous submissions on explicit retry               | A network error or invalid success may happen after the mock accepted an order. Retry resends that exact body and key even if the order already consumed stock. Checkout pauses edits until the result is known. Application-level disabling prevents duplicate clicks, and the mock ledger protects the operation itself.                                                                                                                                                                                                                                                                                           |
| Preserve stock discrepancies visibly                         | Browse data stays fresh for 30 seconds so short revisits reuse it. Cart and checkout request current product details on entry; price and name refresh while requested quantities stay visible. A lower stock count blocks a new checkout until the shopper reduces or removes the item. Orders invalidate product queries, and a 409 updates the affected detail cache and requests fresh stock. Account and order reads are stale immediately and private cache is removed on session changes. See [TanStack Query invalidation](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation). |

## Day 4

| Decision                                                                | Reason and alternative                                                                                                                                                                                                                                                                                                                                                  |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Index all four stable sort orders and materialize only the current page | Profiling showed per-request sorting and stock-row copying were the two slowest handler stages. Extra catalog references at startup trade memory for lower repeat CPU use. See [measurements](performance.md).                                                                                                                                                          |
| Keep pagination at 24 items per page                                    | Chrome confirmed bounded rendering even near the end of the 5,000-product catalog. A virtualizer would add complexity without a measured benefit for this page size.                                                                                                                                                                                                    |
| Use MSW's WebSocket link with REST reconciliation                       | MSW 3.0.7 exports the API from `msw/ws`. A single connection owns updates on shopping routes. Refetching after a valid frame or reconnection keeps counts and filtered pages correct. Patching only the visible product would leave in-stock filtering and page totals stale. See [MSW WebSocket client events](https://source.mswjs.io/docs/websocket/client-events/). |
| Lint the application lane in PR CI                                      | The workflow uses the clean lockfile install and returns actionable app failures. Whole-repository lint still exposes the preserved practice findings. The required check must be configured on GitHub.                                                                                                                                                                 |
| Emit a fixed render-failure event                                       | An exception or component stack can include sensitive values. The boundary records a stable event and offers a page reset with focus recovery.                                                                                                                                                                                                                          |
